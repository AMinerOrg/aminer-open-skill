# SOTA Finder

先交付可用的 Leaderboard。研究说明和证据登记是为了支撑结果，不能取代结果本身。

## 默认方式

- 从用户目标直接开始，先推断一个有用的宽范围，不要先发问卷。
- 除非用户明确限制为“只使用给定材料”，否则默认进行外部检索。
- 如果 benchmark 是套件，或存在明显子任务，应先发现其结构并拆成多个 scope，不要强行给出一个跨任务总榜。
- 用户说“最新”时使用执行当天日期，并写出绝对的证据核验截止日期。
- 每次运行只生成一个最终输出文件夹；研究输入和草稿放在该文件夹之外，不要用重复 bundle 假装阶段性进展。
- 交付优先于可选扩展：已有证据足以覆盖实质 scope 的可用核心时，先写出 working JSON，再决定是否继续查看次要来源。若工具反复停滞、重连或来源失败，应冻结当前范围并用已有材料构建结果，而不是继续扩张。
- 宿主给出的检索截止时间是外部调用的硬停止线。相关查询应成批执行，comparison table 最多扩展一轮；连续 3 个来源检查没有新增重要候选、scope、冲突结论或实际结论变化时必须立即停止，停止门槛触发后不得再做“最后一次检查”。

## 先选择投入层级

检索前按预计研究成本选择 `direct / quick / standard / deep`。这是模型判断，不是固定状态机。

- `direct`：请求并非排行榜任务、现有输入已足够，或工具不可用后有用交付仅限阶段性结构、限制说明与核验计划；立即在聊天中给出实质答案。除非用户明确要求文件，否则到此停止，不读取或执行产物流程。
- `quick`：单一明确 benchmark 或窄 scope，且官方/原始结果面容易获得；尽快交付有用的 Top 3-5，不做全领域综述。
- `standard`：常规 Leaderboard，需要多个来源、用户提供的种子资料、多个明显 scope，或面向实践的候选选择。
- `deep`：没有统一 benchmark、要求宽范围历史/近期覆盖、存在大量竞争 scope，或涉及重要部署与复现约束；广泛检索，但先形成可用核心结果再扩展。

对于周期追踪，没有完整可信基线的首次运行通常使用 `standard`，即使 benchmark 名称很短；已有已校验基线的后续运行通常使用 `quick`：先载入上次证据，把它作为持久候选注册表，再检索截止日期之后的变化。除非一手来源明确显示撤回、更正或协议改变，不得因为本轮未再次搜到就删除历史候选。之前只有 partial 结果时可用它做候选种子，但下一轮仍应按首次基线强度执行。

边界条件与投入层级分开判断：上传文件可能是唯一依据，也可能只是种子；用户要求离线时禁止联网；AMiner 始终可选；冲突和不可访问来源应触发清楚标注，而不是自动升级成更重流程。有文件或 URL 时先用它们，再启用真正能改善答案的来源分支。必须为整理结果和生成产物预留时间，不能把全部时间耗在搜索上。
对于离线结构化文件转换，直接使用给定路径，除明确要求的展示字段外保留原 payload。通过 `research_run.language` 本地化可见文案；机器键、稳定 ID、枚举值，以及 `dataset_or_subtask`、`split`、metric 名称/variant/direction 等脚本依赖值必须保持不变。用户要求时可翻译 topic、scope 名称、标题和说明。Builder 会本地化标准标签和枚举展示值，因此应在校验前准备好可见文案，成功构建后不要再手工修改产物。

原生搜索是默认的发现手段。对于已经找到、但无法直接显示逐行结果的官方动态榜单或文档化数据端点，可按需使用 `<skill-root>/scripts/fetch_source.py <URL>`，把公开文本、HTML、JSON、CSV 或 XML 转为本地可读文件。该工具只限制单次请求以保证安全，不限制研究调用次数；若首次读取落到介绍页或错误赛道，找到正确的直接结果 URL 后可再次调用。其他浏览器或文件工具更合适时由模型自行选择，同时避免没有明确收益的爬站或批量下载。若现有读取器、原生搜索片段或带来源的部分表已足以形成可用结果，不要把交付时间耗在临时编写一次性网页爬虫或解析器上。

任务需要在线研究但宿主没有原生搜索/浏览工具时，可在环境允许时采用与任务相称的直接访问。不要继续翻找无关本地缓存、代理设置或仓库历史来替代在线事实。如果仍无法访问，用一句面向用户的话说明限制，然后展示有实际内容的“暂定/参考榜”，保留已知候选；分数可以缺失或标记为 `unverified`。不要用“0 行主榜”充当结果，也不要暴露代理地址、MCP、插件或认证诊断，除非用户正在排障。

## 检索与建榜

1. **先找榜单入口。** 优先检索官方 benchmark/Leaderboard 页面，再检索原始论文和预印本、官方或作者维护的仓库/Model Card，最后用高质量聚合站发现候选和交叉核对。相关时要让中文名、英文全称、缩写和常见别名实际出现在查询中；能合并时用一次高召回查询覆盖，只有混合查询漏掉独立别名线索或用户明确点名时才单独查询。聚合站不能单独证明主榜结果。
2. **广度优先覆盖 scope。** 建立轻量的“广度优先的 scope inventory”，记录 benchmark/版本、任务或子任务、数据集、split、指标及方向、评测协议、评测执行方/来源，以及真正影响可比性的 setting。官方冻结榜、同一评测方控制的 cross-vendor rerun、各厂商自报评测和不兼容协议结果必须分层展示；除非能证明评测方、实现、输入、推理设置和评分器一致，否则不得合并到同一个 `comparability_complete=true` 主 scope。用户明确点名的 scope 属于主范围：先逐个直接检索，再扩展泛化范围；只有相关官方或一手结果面仍无法恢复结果时，才能记为缺口。首轮让每个实质 scope 获得一个可信榜首或一个具体缺口。比较协议相同的范围应合并，次要范围放入参考表。只恢复出一行结果的 scope 通常不应单独称为排行榜；除非用户明确要求该官方冠军轨道，否则将其折叠为时间线、覆盖表或具体缺口。
3. **建立候选登记。** 对每个有用结果记录方法/变体、原始分数、指标、scope、setting、发表或发布年份、直接来源、表格/段落等定位信息和简短 caveat。深挖任一 scope 前，先完成所有实质 scope 的横向覆盖，再把主范围扩展为证据允许的 Top 3-5；来源原生结果表有多行时，保留全部已恢复的可比行或至少有用的 Top 10。跨 benchmark 或多数据集问题中，如能更清楚地展示已评测与缺失组合，应增加紧凑的 coverage matrix。无法核实的 split、版本、指标或协议应明确写为 `unknown` 或 `unverified`，不要使用模糊占位语，例如 `commonly reported split`。
   来源原生结果表足以支持它直接列出的分数行，不要为每一条复制出来的记录分别打开论文或仓库；深度核验应集中在可能的榜首、可执行的复现候选、实质冲突和不清楚的 setting。用户要求记录某类元数据，并不意味着每一行都必须查全：优先使用榜单来源已有字段，只深入核验会影响结论的候选，其余非关键缺口保留为 `unknown`，不要逐模型串行追查 Model Card 或许可证。只需要少量结果文件时，优先读取指定页面、API 或 raw file，而不是克隆大型结果仓库或批量下载论文；单次网络尝试应保持短小，不要手写重试循环。
   完整性首先指榜单与 scope 覆盖，而不是填满每个元数据单元格。权威结果面是很强的基础，但不是自动停止信号：如果继续查看其他来源可能补充近期候选、用户点名的来源类型、可实践的实现、其他官方赛道，或解决关键不确定性，就应继续。根据下一次研究动作的预期价值与完成整理交付所需时间作判断；低价值元数据可以保留为 `unknown`。
4. **分层但不删除。**
   - `main`：同一实质 scope，分数为数值，比较 setting 足够完整，并有官方、原始论文或作者控制来源。
   - `reference`：有参考价值但 setting 不同或不完整、证据来自二手/聚合来源，或只有候选名称而暂时没有分数。保留在结果中并说明原因。只有聚合站支持的数字绝不能进入 `main`，其 `comparability_complete` 也不能写成 `true`。
   - `unavailable`：明确知道有相关声明，但来源或结果无法访问/还原。不能把所有“需要 caveat”的行都塞进这里。
   - `conflict`：不同来源的数值或解释冲突；保留相关记录并说明处理方式。
5. **定向核验。** 重点核验榜首、近期 SOTA 声明、scope 边界和会改变结论的重要冲突。不必为了“逐篇查完历史”而延迟交付。已有可信 Top 3-5 后，只有新检索可能增加重要候选、改变排名/范围/证据，或补齐用户点名的来源族时才继续；不再重复不会改变结果的来源族。
6. **按可用性停止。** 当每个实质 scope 都有可信表格或明确缺口，主要来源族都已检索或记录缺口，且新增检索不再增加重要候选、也不再解决关键不确定性时停止。连续 3 个来源检查没有实质变化时必须停止。不要因为搜索结果重复就声称“穷尽覆盖”。

**结果优先。** 审计细节留在结构化产物中；聊天和报告使用自然、直接的用户语言，每个实质问题最多给一条紧凑说明，不复述检索过程。证据不完整应改变候选的分组或标签，而不是让有用候选消失。宁可按时交付可用的部分榜单，也不要因追求穷尽核验而没有结果。如果宿主给出了截止时间，把它当成交付约束，而不是查询或来源配额；倒排时间，并在能够完成产物的时点进入整理。

## 最终一致性与降级

回复前只对最终结构化输入做一次轻量检查：聊天数字和状态与其一致，每个 `main` 行都有官方、原始论文或作者控制证据，四个链接指向同一目录。只有证据能证明由不同团队分别执行评测时，才能称为“独立验证”；多个作者控制报告出现相同数字只能说明“多个公开报告一致”。推荐可复现基线时，应区分“官方协议已验证的最强开放模型”和“厂商自报、等待独立复测的新近开放权重候选”。不要为此重开生成产物。如果网络检索或 AMiner 出现鉴权错误、限流、服务缺失或超时，停止重试，记录限制，并用已有证据完成结果。可选来源失败时不能留下空回复。

如果宿主支持真正的中途响应且用户要求先看结果，在找到第一个可信 scope 后先发一版短榜，再继续检索；如果宿主不支持，就在最终回复中按“榜单优先”组织内容，绝不要生成重复正式 bundle 来模拟快照。

## 证据与 AMiner

先直接使用用户提供的文件和 URL，再用开放网络补齐缺口。结构化输入中保留来源角色和证据定位。不能把没有实际执行或宿主无法证明的查询、页面核验或覆盖情况写成既成事实。

AMiner 是可选增强，可用于论文发现、元数据、相关工作和引用扩展，但不能替代官方页面、论文、仓库或普通网络检索，也不能成为开始或完成任务的前置条件。免费或低成本调用可自动执行；预计累计费用约达到人民币 5 元、需要大批量调用或付费不确定时，先确认一次，并记录跳过的内容。

## 交付物

`direct` 跳过本节。对于 `quick`、`standard`、`deep`，或用户明确要求文件时，在最终输出文件夹之外，按照 `references/data-contract.md` 准备一个工作 JSON。获得一批有用结果后就开始写入，并在继续研究时保持它易于收尾；不要等到所有元数据都已查全才开始整理。将面向用户的直接结论写入 `research_run.conclusions`，使简明报告先回答问题，而不是先展示证据机制。

交付前运行校验，只在原文件中修正具体错误，然后正式构建。以简洁的数据契约作为构建指南；除非校验报告了具体问题，不要预读完整 JSON Schema 或 builder 源码，也不要另跑仪式性的语法检查和依赖探测。

```bash
python3 "<skill-root>/scripts/build_outputs.py" \
  --input "/path/to/research-input.json" \
  --output-dir "/path/to/output/bundle" \
  --validate-only
python3 "<skill-root>/scripts/build_outputs.py" \
  --input "/path/to/research-input.json" \
  --output-dir "/path/to/output/bundle"
```

目标是一次校验、一次正式构建。缺少 `openpyxl` 时安装一次 `requirements.txt` 并重试校验。正常运行不要阅读 builder 源码。成功构建即视为 schema、标签、ID 和跨文件一致性已通过：只确认四个路径存在；除非用户要求视觉检查或出现具体不一致，不要用 `sed`、`rg`、`jq`、`wc` 或重开生成文件。一次运行复用已有最终 bundle；实质修订另开新运行。
最终构建是最后一个工作步骤：构建成功后立即根据已完成的 bundle 回复，不再开始新的检索或元数据补查。如果回复前发现具体错误，就修正结构化输入并重新构建；不要只为润色非必要元数据而重新展开广泛检索。

默认在同一文件夹内生成：

```text
brief-report.md       # 聊天结果的扩展版，包含更完整榜单和候选说明
full-report.html      # 完整离线报告
leaderboards.xlsx     # Index + 每个 scope 一个 Sheet
evidence.json         # claim/source/scope 证据登记
```

已有 bundle 时，只有在确实是新的研究运行且已设置新的 `run_id` 时才使用新的 `-2`、`-3` 等目录；同一运行应复用唯一最终 bundle，不覆盖旧结果。如果某个文件生成失败，仍然返回聊天中的可用榜单，并准确说明缺失文件，不能伪造链接。如果 WebSearch、WebFetch、AMiner 或其他可选来源失败，不要停止整个任务或返回空回复；在 `evidence.json` 中记录失败，使用已经收集的证据完成剩余可交付内容。

## 聊天输出

首先清楚给出用户真正想获得的结论。如果需求较宽泛或不够明确，也应根据用户意图总结最有用的信息，例如各范围证据最充分的领先者、是否不存在可直接比较的统一冠军，以及更适合复现或落地的选择；不要以方法说明、审计过程或限制开场。

随后保持简洁但不能残缺：

1. 展示每个实质 scope 的主榜结果；榜单仍便于浏览时尽量完整展示，只有确实较长时才截取有用的头部结果；
2. 用一行说明论文、预印本、仓库或聚合站发现的、但未进入主榜的重要候选；
3. 只补充会改变结果解释的指标、截止日期、冲突或覆盖缺口；
4. 直接链接四个已保存文件。

使用清楚、自然的语言。会影响用户选择、复现或落地的实用信息应尽量保留，例如代码或权重可用性、许可证、硬件或成本、部署限制和关键 setting。聊天中不要展示 evidence ID、来源账本、检索过程、例行校验或防御性说明，也不要粘贴完整报告。不要为了“极简”只展示一个榜首；长榜的完整结果和详细证据放入完整版报告、Excel 和证据文件。只有产物失败或需要用户操作时才说明构建细节。

## 可移植性与边界

用户可见文字跟随用户语言；JSON key、ID、schema value 和稳定机器字段保持英文。Skill 必须自包含、可移植：宿主使用自身搜索/浏览工具，Bundled Python 只处理本地交付物。不建立通用 benchmark 规则库、别名注册表、审批状态机或固定搜索轮数，也不得把实质不可比的开放世界结果混入主榜。
